## Étapes

### Étape 1 : synchroniser les modifications

- Critères d'acceptance couverts : F09-S1-AC1, F09-S1-AC2, F09-S1-AC3, F09-S1-AC4
- Code applicatif :
  - `packages/model/src/ops.ts` : `updateElement` n'écrit que les clés du patch (et les bornes dérivées d'une flèche quand `x1`/`y1`/`x2`/`y2` changent), au lieu de réécrire toutes les propriétés. Sans quoi deux utilisateurs qui déplacent et recolorient le même élément en même temps se recouvrent mutuellement une propriété non modifiée (F09-S1-AC2, ADR-0004, `architecture.md`).
- Code technique : aucun : le socle collaboratif (document Yjs, provider, persistance) et le harnais de fluidité existent (T-003, T-004).
- Code de test :
  - Unitaire : `packages/model/src/ops.test.ts` (`[F09-S1-AC2]` : deux documents convergent après des mises à jour concurrentes de propriétés différentes).
  - Intégration : `apps/server/test/sync.int.test.ts` (`[F09-S1-AC1]` propagation création/modification/suppression entre deux providers réels, `[F09-S1-AC2]` convergence position + couleur entre deux providers réels, `[F09-S1-AC3]` 5 clients × 60 éléments → 300 éléments identiques).
  - E2E : `e2e/board-sync.spec.ts` (`[F09-S1-AC1]` deux contextes navigateur, la création d'un post-it chez l'un arrive chez l'autre dans le délai de FL-4), `e2e/fluidity/board-sync.spec.ts` (`[F09-S1-AC4]` avec 300 ms de latence réseau chez l'utilisateur 1, l'effet local est immédiat et l'utilisateur 2 reçoit tout sans perte).
- Documentation et Markdown : `docs/architecture.md` (mise à jour partielle des éléments et convergence), `docs/journal.md` (décision et tests), `docs/backlog.md` (statut `done`), rapport `docs/test-reports/F09-S1.md` (étape 1).
- Terminée quand : `pnpm verify` est vert (y compris `ac:check` sur F09-S1-AC1 à AC4), deux clients réels convergent après une modification concurrente de deux propriétés du même élément, cinq clients convergent vers 300 éléments, et la création d'un post-it reste locale en ≤ 150 ms malgré 300 ms de latence réseau.
