# Plan : B-001 Mesure FL-2 du pan instable sous charge

- Ticket : [backlog](../backlog.md), détail [B-001](../backlog.md#b-001--mesure-fl-2-du-pan-instable-sous-charge)
- Critères d'acceptance visés : B-001-AC1
- Branche : `bug/B-001-stable-pan-frame-measure`

## Contexte

Le test `[F02-S1-AC4]` (`e2e/fluidity/board-pan.spec.ts`) mesure FL-2 (intervalle médian ≤ 33 ms, aucun intervalle > 200 ms) sur trois exécutions du scénario, puis agrège les intervalles des trois runs en un seul ensemble : la médiane est stable, mais le maximum est celui de l'ensemble fusionné, donc le pic d'un seul run suffit à faire échouer le test. Les mesures consignées (F02-S1, B-003) montrent que la médiane reste autour de 17 ms et que le pic observé (304–411 ms) n'accompagne aucune tâche longue : c'est un aléa de la machine (encodage vidéo, GC, charge), pas un gel applicatif.

F00 (`docs/features/F00-fluidite.md`, « Méthode de mesure ») impose déjà la parade : chaque mesure chiffrée est prise sur 3 exécutions et l'on retient la **médiane des 3**, précisément pour absorber le bruit de la machine sans retry. Le test du pan ne l'applique qu'à la médiane, pas au maximum. Le correctif aligne l'agrégation sur F00 : chaque run produit sa médiane et son maximum, et la valeur retenue est la médiane des trois. Aucun seuil de F00 n'est abaissé, aucun test n'est marqué `skip`.

## Étapes

### Étape 1 : le pic d'un seul run n'échoue plus la mesure FL-2 du pan

- Critères d'acceptance couverts : B-001-AC1
- Code applicatif : aucun : B-001 est un ticket de test, il ne modifie pas l'application.
- Code technique :
  - `tooling/fluidity-stats.ts` (nouveau) : déplace les fonctions pures `median`, `maximum`, `frameStats` de `e2e/support/probe.ts` et ajoute `frameStatsPerRun(runs)` (médiane des médianes et médiane des maxima de chaque run) et `medianOfMaxima(runs)`. Les fonctions pures vivent dans `tooling/` car Vitest exclut `e2e/`, et elles y sont testables unitairement.
  - `e2e/support/probe.ts` : réexporte `median`, `maximum`, `frameStats`, `frameStatsPerRun` et `medianOfMaxima` depuis `tooling/fluidity-stats.ts` ; `installProbe`, `resetProbe`, `readFrameIntervals` et `readLongTasks` restent inchangés. Les specs héritées qui importent ces noms depuis `../support/probe` continuent de fonctionner sans modification.
  - `e2e/fluidity/board-pan.spec.ts` : collecte les intervalles et les tâches longues par run (`number[][]`) au lieu de les fusionner, puis utilise `frameStatsPerRun` et `medianOfMaxima`. Les seuils (médiane ≤ 33 ms, maximum ≤ 200 ms, tâche longue ≤ 200 ms) et les assertions sont inchangés.
- Code de test :
  - Unitaire : `tooling/fluidity-stats.test.ts` (nouveau), cas `[B-001-AC1]` : (1) un run instable sur trois est absorbé (max retenu = celui des deux runs stables) ; (2) deux runs instables sur trois échouent encore (max retenu > 200 ms) ; (3) la médiane des intervalles reste contrôlée ; (4) `medianOfMaxima` absorbe un pic de tâche longue isolé.
  - E2E : `e2e/fluidity/board-pan.spec.ts` (`[F02-S1-AC4]`, hérité) est modifié pour l'agrégation par run, avec les mêmes seuils et assertions (aucun cas ni assertion retiré).
- Documentation et Markdown : `docs/backlog.md` (B-001 `in-progress` puis `done`), `docs/journal.md` (décision + test), rapport `docs/test-reports/B-001.md` (étape 1). `docs/features/F00-fluidite.md` n'est pas modifié : aucun seuil n'est ajusté.
- Terminée quand : `pnpm verify` est vert, y compris `ac:check` ; `e2e/fluidity/board-pan.spec.ts` enchaîné plusieurs fois de suite ne fait plus échouer `[F02-S1-AC4]` sous charge, sans seuil abaissé ni `skip`.
