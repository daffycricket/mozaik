## Étapes

### Étape 1 : persister et le vérifier

- Critères d'acceptance couverts : F09-S2-AC1, F09-S2-AC2, F09-S2-AC3
- Code applicatif : aucun. La persistance demandée par la story existe déjà, livrée par T-003 (`apps/server/src/db/documents.ts`, extension `Database` de Hocuspocus dans `apps/server/src/collab/server.ts`, `updatedAt` mis à jour par `storeDocumentState`). La sonde de reprise (voir Journal) confirme que l'état survit à un redémarrage sur la même base ; l'étape apporte les tests qui rendent ces critères vérifiables et bloquants (`pnpm ac:check`).
- Code technique : `apps/server/test/helpers/server.ts` accepte un chemin de base SQLite optionnel (fichier ou `:memory:`), pour démarrer, arrêter et redémarrer un serveur sur la même base.
- Code de test :
  - Intégration : `apps/server/test/persistence.int.test.ts` (`[F09-S2-AC2]` redémarrage du serveur sur la même base puis nouvel état complet pour un client neuf ; `[F09-S2-AC3]` `updatedAt` mis à jour quand le contenu change et stable sinon).
  - E2E : `e2e/board-persist.spec.ts` (`[F09-S2-AC1]` création d'un post-it, attente de l'enregistrement par l'API, rechargement de la page, éléments identiques).
- Documentation et Markdown : `docs/journal.md` (décision : la persistance de F09-S2 s'appuie sur le socle de T-003, aucun code applicatif), `docs/backlog.md` (statut `done`), rapport `docs/test-reports/F09-S2.md` (étape 1).
- Terminée quand : `pnpm verify` est vert (y compris `ac:check` sur F09-S2-AC1 à AC3), un serveur redémarré sur la même base sert les éléments enregistrés à un nouveau client, et un rechargement de page dans le navigateur retrouve les éléments.
