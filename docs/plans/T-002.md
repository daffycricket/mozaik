## Étapes

### Étape 1 : Outil de rapport `pnpm report`

- Critères d'acceptance couverts : T-002-AC5
- Code applicatif : aucun : outillage uniquement.
- Code technique : `tooling/report.ts` (lecture des JSON, écriture de la section et de `.git/TRAILERS`), script `report` dans `package.json`, sortie JSON de Vitest (`--reporter=json --outputFile`).
- Code de test : `tooling/report.test.ts` (`[T-002-AC5]` : création du fichier, remplacement de section, contenu des trailers, dégradation si une sortie manque).
- Documentation et Markdown : `docs/test-reports/T-002.md` (section 1 écrite à la main, le temps que l'outil soit disponible), `docs/plans/T-002.md` si évolution, `docs/journal.md` (`dépendance`).
- Terminée quand : `pnpm report T-002 --step 1` produit une section conforme et `.git/TRAILERS`, et `pnpm verify` (encore `lint` + `typecheck` + `test:unit`) est vert.

### Étape 2 : Socle serveur SQLite et routes de test

- Critères d'acceptance couverts : T-002-AC7
- Code applicatif : `apps/server/src/config.ts` (validation `zod` de `PORT`, `DATABASE_PATH`, `STATIC_DIR`, `NODE_ENV`), `apps/server/src/db/index.ts` (ouverture SQLite), `apps/server/src/db/migrations.ts` (table `boards`), `apps/server/src/db/boards.ts` (`createBoard`, `resetBoards`), `apps/server/src/app.ts` (routes de test conditionnelles), `apps/server/src/index.ts` (config au démarrage, arrêt propre).
- Code technique : dépendances `better-sqlite3`, `zod`, `nanoid`, `@types/better-sqlite3` ; `allowBuilds` pour `better-sqlite3`.
- Code de test : `apps/server/src/config.test.ts`, `apps/server/src/db/boards.test.ts` (`[T-002-AC7]`).
- Documentation et Markdown : `docs/architecture.md` (structure `db/`, config), `docs/journal.md` (`dépendance`, `décision` sur le périmètre de `seed`).
- Terminée quand : les tests unitaires de config et de la base passent et `pnpm verify` est vert.

### Étape 3 : Harnais d'intégration `test:int`

- Critères d'acceptance couverts : T-002-AC1
- Code applicatif : aucun : harnais de test.
- Code technique : `vitest.int.config.ts`, `apps/server/test/helpers/server.ts` (démarrage réel sur port libre, SQLite `:memory:`), script `test:int`.
- Code de test : `apps/server/test/health.int.test.ts` (`[T-002-AC1]`), `apps/server/test/test-routes.int.test.ts` (`[T-002-AC7]` : routes présentes en test, absentes hors test).
- Documentation et Markdown : `docs/process/testing.md` si la commande diverge, `docs/journal.md` si décision.
- Terminée quand : `pnpm test:int` passe et `pnpm verify` est vert.

### Étape 4 : Couverture `test:cov`

- Critères d'acceptance couverts : T-002-AC3
- Code applicatif : aucun : outillage de test.
- Code technique : `@vitest/coverage-v8`, `vitest.cov.config.ts` (unitaire + intégration fusionnés, seuil 80 % lignes/branches, exclusions justifiées), script `test:cov`.
- Code de test : `tooling/coverage.test.ts` (`[T-002-AC3]` : démontre l'échec sous le seuil sur une fixture non couverte et le succès au-dessus).
- Documentation et Markdown : `docs/process/testing.md` (exclusions), `docs/journal.md` (`dépendance`, `test` si exclusion).
- Terminée quand : `pnpm test:cov` passe et échoue bien sur une fixture volontairement non couverte, puis `pnpm verify` est vert.

### Étape 5 : Harnais e2e Playwright

- Critères d'acceptance couverts : T-002-AC2
- Code applicatif : aucun : harnais de test.
- Code technique : `@playwright/test`, `playwright.config.ts` (`webServer` serveur + Vite, `VITE_E2E=1`, base SQLite temporaire), `tooling/ensure-playwright-browsers.ts` (installe Chromium s'il est absent), scripts `start` par app et `test:e2e`.
- Code de test : `e2e/home.spec.ts` (`[T-002-AC2]` : l'accueil affiche le nom de l'application).
- Documentation et Markdown : `docs/process/testing.md` si la commande diverge, `docs/journal.md` (`dépendance`, `décision` sur le mode de lancement e2e).
- Terminée quand : `pnpm test:e2e` passe et `pnpm verify` est vert.

### Étape 6 : Traçabilité, `verify` et clôture

- Critères d'acceptance couverts : T-002-AC4, T-002-AC6, T-002-AC8
- Code applicatif : aucun : outillage.
- Code technique : `tooling/ac-check.ts` (lit `docs/features/*.md`, `docs/design/ecrans.md` et les critères `T-NNN-ACN`, lit les statuts de `docs/backlog.md`, cherche les identifiants dans les titres de tests, bloque sur `in-progress`/`done`), `tooling/verify.ts` (ordre lint → typecheck → test:cov → test:e2e → ac:check, arrêt au premier échec), scripts `ac:check` et `verify`, retrait de l'exception `n/a (T-001)` dans `tooling/commit-msg.ts`.
- Code de test : `tooling/ac-check.test.ts` (`[T-002-AC4]` : fixtures couvertes/non couvertes, blocage selon le statut, règles `UI-*`), `tooling/verify.test.ts` (`[T-002-AC6]` : ordre des commandes et arrêt au premier échec), mise à jour de `tooling/commit-msg.test.ts` (`[T-002-AC8]` : `n/a` refusé pour tous les tickets).
- Documentation et Markdown : `docs/backlog.md` (T-002 `done`), `docs/journal.md` (`test` pour le test hérité modifié, `décision`), `docs/process/git.md` et `docs/process/testing.md` si la commande diverge.
- Terminée quand : `pnpm ac:check` passe, `pnpm verify` est vert de bout en bout, et un message `n/a` est refusé par le hook.
